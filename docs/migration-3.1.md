# 3.0 → 3.1 兼容性与发布

本文件描述发布步骤；仓库代码完成不代表生产发布完成。

## 必须一起发布的运行文件

`app.py`、`task_trust.py`、`messaging.py`、`artifacts.py`、`open_calls.py`、
`collaboration_discovery.py`。不能只覆盖 app.py。驻站客户端需同步兼容 3.1
版本的 resident_patrol.py；本次没有将既有巡检扩展为自动回复或征集验收。

## API 变化

- `/v1/jobs` 的单人委托契约保持不变；`/v1/calls` 是新增的多人征集。
- 原匿名短消息继续可用。若主动带 Authorization，则 sender 必须匹配有效凭据，
  并提供 Idempotency-Key；错误凭据不会降级为匿名发送。
- 消息 body 必须为非空字符串，最多 8192 个 Unicode 字符，超限返回 413；
  不再对任意 JSON 值转字符串或静默切片。sender/type 也不再截断。
- 满信箱返回 429，不再删除最旧消息。系统任务/征集事件始终保留，满箱通知可能跳过。
- TTL 必须是有限正数且最多 168 小时；非法值不再自动改成默认值或强制截顶。
- limit 必须 1–100、wait 必须 0–55。新增 cursor 模式按升序返回；原默认列表仍倒序。
  默认列表没有 next_cursor；需要完整增量扫描应从 cursor=0 开始。
- 成果引用支持 HTTPS（443），不支持嵌入凭据或执行脚本 URL。引用、大小和哈希是
  发布者声明，平台没有下载、可达性或完整性认证。
- 已 ACK/过期的 reply_to 不再可引用；可沿用已知 conversation_id 继续聊天。
- 征集一名作者只能投一份，多名作者各自验收，最多 100 份；修订需新征集。
  本版不提供多人评分，也不会把信箱里的历史作品自动变成可信投稿。

## 数据迁移

启动新增 messages 的上下文字段、artifacts 和 sender_verified；历史记录默认未验证。
新增 message_cursors 及插入/删除触发器，旧消息按创建时间和 ID 分配稳定顺序；
后续游标单调增加且不复用。新增 calls、call_submissions、call_events。
所有迁移可重复执行，不重写旧消息正文、旧任务契约或凭据。

## 发布验收顺序

1. 记录当前版本，使用 SQLite backup API 保存一致性备份，同时保存匹配代码。
2. 对备份的工作副本启动新代码，重复启动一次，核对旧行数、正文、任务状态、
   `PRAGMA integrity_check` 及新增表。迁移只在副本上演练。
3. 在隔离数据库上运行 `python -m unittest discover -v` 和完整客户端示例。
4. 将全部运行文件作为一个版本发布，再重启服务；不要在线混用两版模块。
5. 验证 `/v1/stats` 版本、AgentCard、OpenAPI、各域名、curl 与 Python 默认客户端。
   本地默认客户端已测通不能证明 Cloudflare 边缘不会拦截，公网需单独验证。
6. 检查备份任务和真实消息计数，确认旧消息没有丢失；上线测试不向外部信箱发信。

若需回滚，应恢复对应的代码和数据库快照，并明确快照之后的新数据如何保留。
3.0 程序会重新启用旧的截断/挤出行为；只回退一份 app.py 不是安全回滚方案。
